Week 10 — Working with the Database: CRUD, Queries and Data-Driven Pages

Week 10 was about the data layer of the team project: describing tables in Python, then creating, reading, updating and deleting rows safely. It also introduced the most important security check for any site where users own data: making sure a user can only see and change their own rows.

The examples use the team project's Favorite table, where each row is an item a user saved.

2. The ORM: Python objects become database rows

PythonDatabase
db = SQLAlchemy()The database connection
class Favorite(db.Model)The table favorite
one Favorite() objectOne row
fav.item_titleThe column item_title

SQLAlchemy is an ORM (Object-Relational Mapper): it translates between Python objects and database rows, so no SQL has to be written by hand. Changing fav.item_title only changes the object in memory until the change is committed.

3. Setting up the database in 5 steps

# models.py
db = SQLAlchemy()                     # 1. create the db object (not connected yet)
class User(db.Model): ...             # 2. describe each table as a class

# app.py
app.config["SQLALCHEMY_DATABASE_URI"] = database_uri()   # 3. where is the database?
db.init_app(app)                      # 4. connect db to this app
with app.app_context():
    db.create_all()                   # 5. create the tables that don't exist yet

There is one db object in the whole project: created once in models.py, connected once in app.py, and imported everywhere else with from models import db. The same code uses PostgreSQL on Render and a local SQLite file on a laptop.

db.create_all() never changes a table that already exists. After adding a column to a model, reset_db.py (drop + create) must be run, otherwise the app fails with "no such column".

4. Describing a table

class Favorite(db.Model):
    id         = db.Column(db.Integer, primary_key=True)
    item_id    = db.Column(db.String(50), nullable=False)   # the API's id
    item_title = db.Column(db.String(255))
    item_image = db.Column(db.String(500))
    user_id    = db.Column(db.Integer, db.ForeignKey("user.id"), nullable=False)
    __table_args__ = (db.UniqueConstraint("user_id", "item_id"),)   # no duplicates
  • primary_key=True: the unique id of each row.
  • nullable=False: the column is required.
  • db.ForeignKey("user.id"): links each favourite to the user who saved it.
  • UniqueConstraint("user_id", "item_id"): the same user cannot save the same item twice. It covers two columns together, so it goes in __table_args__, where table-level rules live.

5. CRUD: Create, Read, Update, Delete

Writing goes through db.session, a pending list of changes:

db.session.add(obj)       # stage a new row       (Create)
db.session.delete(obj)    # stage a removal       (Delete)
db.session.commit()       # write every staged change ("save")
db.session.rollback()     # throw the pending list away ("undo")
  • Create: build a new object, add it, then commit.
  • Update: change the attribute of a loaded row, then commit (no add: the session already tracks it).
  • Delete: delete the loaded row, then commit.

Nothing is saved until db.session.commit(), which writes all pending changes as one unit.

Reading goes through Model.query. The query is built step by step and only runs at the end:

Favorite.query
    .filter_by(user_id=3)            # narrow it
    .order_by(Favorite.item_title)   # sort it A to Z
    .all()                           # NOW it runs
EndingReturns
.all()A list of every match
.first()One row, or None
.count()How many rows match
.get_or_404(id)One row by id, or a clean 404 page

6. Querying

  • filter_by(user_id=3, item_id="52772"): short form for simple equality, conditions joined with AND.
  • filter(Favorite.rating >= 4): for real comparisons such as greater-than or not-equal.
  • .order_by(Favorite.id.desc()) sorts newest first, and .limit(10) keeps the first 10.
  • get_or_404(id) is used whenever a route takes an id in the URL: a missing id gives a 404 instead of a crash.

A case-insensitive search of the user's own saved items, where % means "anything here":

q = request.args.get("q", "").strip()
results = (Favorite.query
           .filter_by(user_id=session["user_id"])          # only this user's rows
           .filter(Favorite.item_title.ilike(f"%{q}%"))   # title contains q
           .all())

7. The ownership check (the security idea of the week)

fav = Favorite.query.get_or_404(fav_id)       # the row EXISTS...
if fav.user_id != session["user_id"]:          # ...but is it YOURS?
    abort(403)

get_or_404 proves the row exists, not that it belongs to the user. Without this check, a logged-in user could open /favorites/42/edit, change 42 to 43 in the address bar, and edit someone else's data. Hiding the Edit link does nothing, because anyone can type the URL. This bug is called IDOR (Insecure Direct Object Reference), one of the most common real-world web vulnerabilities.

Every route that loads a row by id and then shows or changes private data needs an ownership check.

Status codeMeaning
401 UnauthorizedNot logged in (@login_required redirects to log-in)
403 ForbiddenLogged in, but the row is not yours
404 Not FoundThe row does not exist

8. Handling what goes wrong

from sqlalchemy.exc import IntegrityError

try:
    db.session.add(fav)
    db.session.commit()
    flash("Saved.")
except IntegrityError:            # e.g. the same item saved twice
    db.session.rollback()         # clean the session first
    flash("You already saved that item.")

An IntegrityError happens when a write breaks a database rule, such as the unique constraint. If a commit fails, the session must be rolled back before anything else, or the next request inherits the half-done change.

flash() is a one-time message. After a POST the route redirects (so refreshing the page does not submit the form again), and flash carries the message across that redirect so the next page shows it once.

9. Data-driven pages and the round trip

A data-driven page gets its content from the project's own database rather than from the external API. For example, a profile page shows the user's email, their saved items sorted A to Z, and how many there are.

Every database-backed page follows the same path:

Browser request -> @app.route in app.py
                -> build a query / change a row
                -> db.session.commit()   (if writing)
                -> render_template(..., data=...)
                -> HTML back to the browser

Reads use GET. Writes (create, update, delete) use POST, because a change to the server's data should never happen just from clicking a link.

10. Common mistakes

MistakeWhat happens
Forgetting commit()The change disappears on the next request
add() on an updateNot needed: only new rows are added
Skipping the ownership checkAnyone edits anyone's data by changing the id (IDOR)
.get() instead of get_or_404()None, then a crash on the next line
Querying without the user filter.all() returns everyone's rows
No rollback() after a failed commitThe next request inherits the broken session
Trusting the HTML formA direct POST skips it, so the server must re-check
Editing a model without rebuilding"no such column" at runtime
