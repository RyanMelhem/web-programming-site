Week 11 — Web Security

Week 11 was about attacking and defending web applications. It is organised around the OWASP Top 10 (2025), the industry's list of the ten most critical web-app security risks. For each risk the week showed how the attack works and how to close it in a Flask app. At the end, this portfolio site went through its own security review (section 11).

1. The OWASP Top 10:2025

OWASP (Open Worldwide Application Security Project) is a non-profit security community. Its Top 10 is built from real breach data and gives developers a shared vocabulary. It is a starting point, not a complete checklist.

2. Three golden rules and the attacker's mindset

  • Never trust input. Form fields, URLs, cookies and JSON can all be hostile. Validate them and escape them for wherever they go.
  • Least privilege. Every user, route, token and database account gets only the access it needs.
  • Defence in depth. Never rely on one control; if one fails, the next one catches it.

For every feature, ask four questions: What is the input? Where does it go? What could a malicious value do there? Who can reach this route?

3. Injection (A05)

Injection happens when untrusted input is treated as code instead of data. The cause is always the same, mixing data and code in one string, and so is the cure: keep them separate.

SQL injection. Gluing user text into a query lets the user rewrite it:

# NEVER do this
query = f"SELECT * FROM user WHERE email = '{email}'"

# typing  ' OR '1'='1   matches every row -> the whole table leaks
# typing  admin@site.com' --   comments out the password check -> log-in as admin

The fix is to use the ORM or bound parameters, so the input can only ever be a value:

rows = Favorite.query.filter(Favorite.item_title.ilike(f"%{q}%")).all()   # ORM: safe

db.session.execute(text("SELECT ... WHERE item_title LIKE :pat"),
                   {"pat": f"%{q}%"})                                     # bound parameter: safe

OS command injection. Passing a filename into os.system(f"convert uploads/{name} ...") lets photo.png; rm -rf / run a second command on the server (remote code execution). The fix is subprocess.run([...]) with the arguments as a list, so nothing is parsed by a shell, plus validating the filename.

Server-side template injection. Building a template from user input with render_template_string lets {% raw %}{{7*7}}{% endraw %} be evaluated (the page shows 49), and from there the attacker can read the app's secrets. The fix is render_template("hello.html", name=name), so the input is passed as data and escaped.

Never paste user input into a query, a command, or a template string.

4. Cross-Site Scripting (XSS)

XSS means an attacker's JavaScript runs in another user's browser, on your site, where it can steal cookies or act as the victim. The attacker simply uses a normal feature, such as a note or a bio, and types a script instead of text.

  • Stored XSS: the script is saved in the database and runs for everyone who views the page. The most dangerous kind.
  • Reflected XSS: the script rides in a link (?q=<script>...) and bounces back into the page.
  • DOM-based XSS: the browser's own JavaScript writes attacker HTML, for example with innerHTML.

Jinja escapes everything printed with double braces by default, so <script> is shown as harmless text. The danger is turning that off: never use | safe or Markup() on anything a user supplied, and in JavaScript use textContent rather than innerHTML for user data. Escaping also has to fit where the value lands: inside <script> use | tojson, and in links block javascript: URLs. If some HTML must be allowed, it is cleaned to an allow-list of tags with bleach.

A Content-Security-Policy header is the second line of defence: it tells the browser which scripts may run, so an injected script is refused even if it slips through.

5. Insecure Design (A06)

A design flaw cannot be fixed with one line, because the idea itself is wrong. Examples: a log-in with no limit on attempts, a password-reset link that never expires, a checkout that reaches "success" without payment, or trusting a price sent from a hidden form field. The fix for that last one is not escaping the price, it is never trusting it: the server looks the price up itself. Security is designed in from the start, through threat modelling and security requirements.

6. Broken Access Control (A01), the number one risk

  • Authentication asks who are you? (@login_required). Authorization asks what may you touch? (the ownership check). One without the other is a lock that opens for everyone once they are inside.
  • IDOR: changing an id in the URL to reach someone else's row. Fixed by the ownership check, which returns 403.
  • Missing function-level checks: an admin page protected only by @login_required is open to every user. It must also check the user's role.
  • Forced browsing: attackers guess URLs like /admin or /backup.zip. A page not being linked anywhere is not protection; the route must check every time.
  • CSRF also belongs here: every form that changes data needs a CSRF token.

7. Security Misconfiguration (A02)

  • Debug mode in production turns any error into an interactive Python console. Debug is read from an environment variable and stays off on the live site.
  • Secrets in Git are public forever, because the history keeps them. Keys and database URLs go in environment variables, and .env and *.db go in .gitignore. A leaked key is rotated, not just deleted.
  • A weak SECRET_KEY such as "dev" lets attackers forge session cookies. It is generated with secrets.token_hex(32).
  • Cookie flags: HttpOnly, Secure, SameSite="Lax" and a session time limit.

8. Cryptographic Failures (A04)

HTTPS protects data in transit (with HSTS telling browsers to always use it), and passwords are stored as salted, slow, one-way hashes. The things not to do: invent your own cryptography, hash passwords with MD5 or SHA-1, treat Base64 as encryption (it is only an encoding anyone can reverse), or log a password or token.

9. Supply Chain (A03) and Integrity (A08)

A web app ships other people's code: Flask, SQLAlchemy, gunicorn and everything they depend on. A vulnerability in any of them is a vulnerability in the app. The defences:

pip install -r requirements.txt   # install only what is listed
pip list --outdated                # what has a newer, safer release
pip-audit                          # scan for known vulnerabilities

Versions are pinned in requirements.txt (for example Flask==3.1.3) so every build is the same, dependencies are kept to a minimum, and package names are checked carefully against look-alikes. For integrity, untrusted data is read with json, never pickle, which can execute code.
