Week 12 — Responsive Design, UI/UX & Accessibility

Week 12 was about making a site work for every screen and every person: phones as well as laptops, keyboard users as well as mouse users, screen-reader users as well as sighted users. The method was audit first, fix, then re-audit, so every change is measured instead of guessed. This page records what was found on this portfolio site and what was changed.

1. The three areas

  • Responsive design: one site that adapts to any screen: the viewport tag, fluid widths (width:100% + max-width), rem units, media queries, a responsive grid and images that never overflow.
  • UI / UX: clear visual hierarchy and spacing, real labels, visible :hover / :focus / :disabled states, and a loading, success and error state for every data feature.
  • Accessibility (a11y): semantic HTML, labels linked to inputs, full keyboard use with a visible focus outline and a skip link, contrast of at least 4.5:1, alt text, and role="alert" for messages that appear.

WAVE: 0 errors, 0 contrast errors, 0 alerts. The only automated issue was SEO: "Document does not have a meta description".

Automated tools only check what a program can detect. They cannot tell whether a phone user can see the page past the header, whether there is a skip link, or whether a failed request leaves a frozen screen. Most of this week's fixes came from the manual checklist, not from the scores.

3. Design decisions

Decided before asking the AI to help implement anything:

  • Header on phones: the 14 navigation buttons filled most of a phone screen, so they collapse behind a ☰ Menu button on small screens. The header stays sticky.
  • Footer: no longer fixed to the bottom of the screen; it sits after the content like a normal footer.
  • Links in text: always underlined inside paragraphs, so a link is never shown by colour alone. Navigation buttons and Weekly Work cards already look clickable, so they keep the hover underline.

4. Responsive fixes

Collapsible menu. A real <button> is linked to the nav with aria-controls, and aria-expanded tells screen readers whether the menu is open:

<button type="button" class="nav-toggle"
        aria-expanded="false" aria-controls="site-nav">☰ Menu</button>
<nav id="site-nav" aria-label="Main"> ... </nav>

The script lives in static/nav.js, not in an onclick, because the Week 11 Content-Security-Policy blocks inline JavaScript:

document.documentElement.classList.add('js');
const button = document.querySelector('.nav-toggle');
const nav = document.getElementById('site-nav');
button.addEventListener('click', function () {
    const isOpen = nav.classList.toggle('is-open');
    button.setAttribute('aria-expanded', isOpen);
});

The CSS hides the nav only when <html> has the class js. If JavaScript fails to load, the button stays hidden and the full nav stays visible, so the site never has a menu that cannot be opened.

Footer moved from position: fixed into the normal page flow, which also removed the 6rem padding that kept content clear of it.

Images: img { max-width: 100%; height: auto; } was added so a future image can never overflow a phone screen. The site currently has no images, so there was no alt text to fix.

Already in place from Week 3: the viewport tag, sizes in rem, mobile-first media queries, a capped main width and the repeat(auto-fit, minmax(240px, 1fr)) grid for Weekly Work.

5. UI / UX fixes

  • Live Quiz error state: the error message was plain grey text that looked like any paragraph. It is now a red box with a red bar on the left (contrast about 5.5:1), and "Loading…" is shown in italics.
  • States already present: the Live Quiz already had loading, success and error states from Week 7, and the quiz buttons already had :hover and :disabled styles.
  • Meta description added in base.html, which fixes the SEO issue on every page at once.

6. Accessibility fixes

  • Skip link: the first thing the Tab key reaches is a hidden "Skip to main content" link. It appears when focused and jumps to <main id="main">, past the 14 navigation links.
  • Visible focus: links, buttons and form fields get a thick 3px outline with :focus-visible, so keyboard users always see where they are. The outline is never removed.
  • One main landmark: both quiz pages had their own <main> inside the one from base.html. They now use a <div class="container">.
  • Announced messages: the Live Quiz error has role="alert", "Loading…" has role="status", and the server-validation summary on the profile form has role="alert", so screen readers read them out when they appear.
  • Links in text underlined: links no longer rely on colour alone.
  • Already correct: header / nav / main / footer, real buttons, and a <label for> on every form field, with <fieldset> and <legend> around the radio and checkbox groups.

7. Testing

  • Chrome device toolbar at phone, tablet and desktop widths: menu closed and open, footer position, no sideways scrolling.
  • Keyboard only: Tab reaches the skip link first, Enter jumps to the content, the menu opens with Enter, and the focus outline is visible everywhere.
  • Error states: stopping the server and clicking Next in the Live Quiz shows the red error box instead of a frozen page; submitting the validated form empty shows the error summary.
