Week 9 — Team Project, Accounts and Security Basics

Week 9 started the team project. Until then, every page on this site was built alone; from Week 9 on, the main work happens in a team repository. The week also introduced user accounts (sign-up, log-in, log-out) and the security basics that every site with accounts needs: hashed passwords, protected routes, safe session cookies, CSRF protection and HTTPS.

This page summarises what Week 9 covered. The team project's code lives in the team repository, not on this portfolio site.

1. The team project

Our team of three is building Brom el ARD, an AI travel-planning companion: users browse destinations and activities with prices, previews and ratings, save favourites, and ask an AI travel advisor to plan a trip from a simple prompt.

Before writing code, the team wrote requirements in two groups:

  • Functional requirements — what the site does (search destinations, save favourites, log in...).
  • Non-functional requirements — how well and how safely it does it (security, performance, usability). Security requirements belong here, next to the functional ones, so security is designed in from the start instead of added at the end.

Thinking like an attacker for each feature — what is the input, where does it go, who can reach it — is called threat thinking, and it shapes those requirements.

2. Sign-up and log-in with sessions

HTTP does not remember who you are between requests. After a successful log-in, Flask stores the user's id in the session, a signed cookie that the browser sends back with every request:

{% raw %}# on successful log-in
session.clear()                 # drop any old session first
session["user_id"] = user.id    # now every request knows who you are

# on log-out
session.clear()                 # forget the user completely{% endraw %}

The session cookie is signed with the app's SECRET_KEY, so a user cannot edit it to pretend to be someone else — as long as that key is long, random and kept secret in an environment variable.

3. Password hashing

Passwords are never stored as they were typed. They are stored as a salted, slow, one-way hash:

from werkzeug.security import generate_password_hash, check_password_hash

# sign-up: store the hash, never the password
user.password_hash = generate_password_hash(password)

# log-in: compare what was typed with the stored hash -> True / False
check_password_hash(user.password_hash, password)
PropertyWhy it matters
One-wayThe hash cannot be turned back into the password.
SaltedA random value per user, so two users with the same password get different hashes and precomputed "rainbow tables" are useless.
SlowEach guess is expensive, so mass password guessing becomes impractical.

If the database ever leaks, attackers get hashes, not passwords.

4. Protecting routes with @login_required

Pages that belong to a logged-in user are protected by a decorator that runs before the route. If nobody is logged in, it redirects to the log-in page instead of running the route:

@app.route("/favorites")
@login_required          # checks that session["user_id"] is set
def favorites():
    ...

This is authentication: who are you? Week 10 added the second half, authorization: is this row yours?

5. Generic log-in errors

A log-in form should never say "no such user" for one case and "wrong password" for the other. That tells an attacker which emails have accounts. One message is used for every failure:

error = "Email or password is incorrect."

6. Safe session cookies

The session cookie gets three safety flags and a time limit:

app.config.update(
    SESSION_COOKIE_HTTPONLY=True,     # JavaScript cannot read the cookie (blocks XSS theft)
    SESSION_COOKIE_SECURE=True,       # only sent over HTTPS
    SESSION_COOKIE_SAMESITE="Lax",    # limits sending it from other sites (helps against CSRF)
    PERMANENT_SESSION_LIFETIME=timedelta(minutes=30),
)

7. CSRF protection

Cross-Site Request Forgery tricks a logged-in user's browser into submitting a request they never intended — the browser attaches their session cookie automatically. The fix is a secret token in every form that changes data, which another site cannot know:

{% raw %}from flask_wtf.csrf import CSRFProtect
csrf = CSRFProtect(app)   # every state-changing POST now needs a token

<form method="post">
  <input type="hidden" name="csrf_token" value="{{ csrf_token() }}">
  ...
</form>{% endraw %}

8. HTTPS

HTTPS encrypts the connection, so passwords and session cookies cannot be read on the network. Render serves every site over HTTPS automatically. Hashing protects passwords stored in the database; HTTPS protects them in transit — a log-in form must never be sent over plain http://.
